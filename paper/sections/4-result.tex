\section{Integration and Evaluation}
\label{sec:evaluation}

This section describes the integration of \texttt{Rust2Isabelle} into Aeneas and evaluates its translation coverage.
The Aeneas regression suite is used to examine specific Rust features, while the case study considers larger components from a real-world system, Solona Berkeley Packet Filter (SBPF) blockchain virtual machine.
The evaluation concerns generation and acceptance of Isabelle theories.

\subsection{Integration and Feature Coverage}

\texttt{Rust2Isabelle} is integrated into Aeneas as an Isabelle/HOL backend and selected using the option \texttt{-backend isabelle}.
The regression tests invoke this backend to generate complete Isabelle theories importing the \rprelude{}.

The Isabelle backend adds approximately 2.7~kLoC of OCaml to Aeneas.
It implements Isabelle-specific naming and built-in mappings, together with the translation of Pure declarations into complete theory files.
The accompanying \rprelude{} comprises approximately 1.5~kLoC of Isabelle/HOL definitions for Rust primitives and predefined library operations.

We evaluated the backend using regression tests from Aeneas.
Isabelle successfully processed 26 generated theories, covering the Rust features summarized in \autoref{tab:feature-coverage}.
Since Isabelle/HOL and HOL4 are closely related HOL-based theorem provers, the table also compares the feature support of their Aeneas backends.
The HOL4 results are based on its implementation and previously generated theories because it is not currently enabled in the Aeneas test suite.

The results show that the Isabelle backend supports the main Pure types, expressions, borrowing constructs, and control-flow forms covered by the selected tests.
It matches the HOL4 backend on their shared features and provides broader support for const generics, trait dictionaries, scalar operations, arrays, and nested borrowing and control flow.
Both backends reuse Aeneas's functional representation of mutable borrows.

The remaining disadvantage relative to HOL4 concerns potentially diverging functions.
The HOL4 result type distinguishes successful execution, failure, and divergence, allowing recursive functions to be represented without first proving termination.
The Isabelle backend supports singly and mutually recursive functions when Isabelle can establish termination, but it does not yet represent genuinely divergent executions explicitly.

These results confirm that the backend implements the translation described in \autoref{sec:design} across the supported features.
A mechanized end-to-end proof of semantics preservation remains outside the scope of this work.

\subsection{Case Study: Solana JIT Compiler}
\label{sec:SBPF-case-study}

Our case study considers the SBPF just-in-time (JIT) compiler, a core component of the Solana blockchain virtual machine that translates SBPF instructions into x86-64 code~\cite{anza2026SBPF}.
Because the x86 instruction encoder is a direct dependency of the compiler, we translate both components.
Their production implementations use unsafe Rust for raw pointers, executable memory, and function pointers, which lie outside the fragment supported by Aeneas.
We therefore retain their principal encoding and compilation logic while replacing these operations with safe Rust representations.
The encoder returns bytes in a \texttt{Vec<u8>}, while the JIT uses owned vectors and integer offsets instead of executable memory and raw addresses.
To restrict extraction to these adapted components, we select \texttt{X86Instruction::encode} and \texttt{compile\_sbpf} as translation entry points.
Charon starts from these functions and retains only the declarations on which they depend.
\autoref{tab:SBPF-results} summarizes their translation results.

The Rust LOC counts only local source lines referenced by the generated declarations, with overlapping ranges counted once.
It excludes untranslated parts of the source files and Rust standard-library code.
In contrast, the Theory LOC includes every declaration in the generated \texttt{.thy} file, including required library types and operations, whether they have concrete definitions or are introduced by \texttt{axiomatization}.
The separately imported \rprelude{} is not included.

For the x86 encoder, the 163 Rust lines consist of 151 lines from the encoder and 12 lines defining an operand-size dependency.
Its 551-line theory additionally introduces the library types, traits, and operations required by the encoding function.
For the JIT model, the 1,141 Rust lines comprise 680 lines of JIT logic, 441 lines of x86 encoding code, and 20 lines of SBPF instruction definitions.
Unlike the encoder entry point, the JIT entry point reaches many functions for decoding instruction classes, selecting x86 instructions, emitting bytes, recording jump targets, and resolving relative offsets.
The translation represents every instruction branch as an explicit conditional or case expression, chains operations that may fail through the result monad, and expresses changes to the compiler state as record updates.
Loops also introduce separate definitions for the loop body and its invocation.
Together with the required x86 and SBPF declarations, these explicit representations expand the model to 3,483 lines of Isabelle.


The two theories contain 11 and 24 \texttt{axiomatization} commands, respectively, for required library operations that lack definitions in the current \rprelude{}.
Each command introduces a typed constant without a function body, so these commands account for only a small part of the increase in line count.
Most of the increase comes from concrete definitions and from expressing Rust operations explicitly in functional form.
The components still exclude executable-memory allocation, raw memory access, indirect function invocation, instruction metering, and unsupported SBPF instructions.
The case study therefore demonstrates automatic translation of a substantial safe subset of the SBPF JIT, rather than verification of its complete production implementation.
